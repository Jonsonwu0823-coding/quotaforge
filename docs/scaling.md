# 两个实例和压测

## 两个实例

`compose.two.yaml` 叠加在 `compose.yaml` 上，再起一个 QF 实例 `quotaforge-b`：

```bash
# 在项目根目录下运行
docker compose -f compose.yaml -f compose.two.yaml up -d --build --wait
curl -sS http://127.0.0.1:8080/healthz   # quotaforge
curl -sS http://127.0.0.1:8081/healthz   # quotaforge-b
docker compose -f compose.yaml -f compose.two.yaml down -v
```

- **共享什么**：两个实例是同一个镜像、同一份配置、同一个 `app_dsn`，共用 `qf-mysql`（额度、账本、幂等记录）和 `qf-redis`（限流的桶）；开了[嵌入缓存](api.md#嵌入缓存)时也共用缓存的 Redis（`qf-redis-cache`），一个实例写进去的，另一个实例也能命中。除了上游的熔断和嵌入缓存的合并，进程里没有会让两个实例结果不一致的状态：每个请求都查库鉴权，没有 Key 和额度的本地缓存；限流只在 Redis 的脚本里算，时间只取 Redis 的 `TIME`。
- **嵌入缓存的合并只在实例内**：同一个实例里同时到的相同嵌入请求只回源一次，跨实例的不合并，两个实例同时没命中、第一个请求成功时各回源一次（最多两次）。不在 Redis 里加锁做跨实例合并：要多一套锁的过期和持有者挂掉之后的处理，省下的只是并发时多出的一次回源。缓存不影响额度和账本：命中只写一条 `CACHED`、不动额度，两个实例各自写的 `CACHED` 都由账本的不变量检查（`qfctl verify`）。
- **熔断每个实例各记各的**（见[多个上游](operations.md#多个上游)）：它只决定“这个实例试不试某个上游”，不碰额度和账本，结局仍由账本的条件更新保证。两个实例可以短时间不一致：上游刚挂时，一个实例已经打开、另一个还在一个个试；上游恢复后，各自过了冷却、各自探测一次才关上。请求一个接一个来时，每个实例最多多试 `failure_threshold` 次、多等一个冷却，之后就收敛；并发时多试的次数可以更多（见[多个上游](operations.md#多个上游)的“熔断”）。不放进 Redis：限流的 Redis 只做限流，放进去要多一个职责，Redis 不可用时还得另定熔断怎么办；放进 MySQL 则每个请求多一次查询。指标 `qf_upstream_circuit_state` 按实例看（Prometheus 的 `instance` 标签）。
- **写法**：`quotaforge-b` 用 `extends` 引用 `compose.yaml` 里的 `quotaforge`，安全设置、依赖（迁移成功、Redis 健康）、secret、`stop_grace_period` 只写一份；去掉 `build`（用同一个镜像）、换掉端口（`!override`，只发布 `127.0.0.1:8081`）。`extends` 要写明 `file: compose.yaml`：它只看那个文件，不看合并之后的项目。要 Compose v2.24 以上（`!reset`、`!override`）。
- **不接 `qs-qf`**：QS 的两个覆盖文件只改 `quotaforge`，`quotaforge-b` 只在 Compose 的默认网络上。叠上 `compose.qs-e2e.yaml`（只给端到端联调用，见[接 QueryShield](queryshield.md)）时才接进 `qs-qf`，带网络别名 `quotaforge`。
- **没有负载均衡器**：测试和压测工具自己轮流发给两个实例。负载均衡器会多一层超时、断开和请求体上限的行为，这里要证明的是两个进程共享状态时的正确性。
- **后台循环**：两个实例各自跑回收和清理，和生产一样（见[调用状态、回收和对账](ledger.md#调用状态回收和对账未知用量)）。
- **压测工具** `qfbench`（`cmd/qfbench`，只用标准库）也在这个文件里，`profiles: [tools]`，`up` 不起它，只用 `docker compose run`。它在 Compose 网络里面发请求，不经宿主机的端口转发：

  ```
  qfbench sustain   -target URL [-target URL…] -body JSON [-body JSON…] -c N -warmup 5s -duration 30s [-timeout 30s] [-idem-each]
  qfbench burst     -target URL [-target URL…] -body JSON [-body JSON…] -n N [-idem-key K | -idem-each] [-timeout 60s]
  qfbench summarize   # stdin 是原始数据，stdout 写汇总 JSON
  ```

  - `sustain` 是闭环压测：C 个并发各自发完一个再发下一个，开始时间在预热期内的标为预热；`burst` 是齐发：每个请求自己的连接，先 `GET /healthz` 把连接建好，全部就绪后在一个屏障处一起放开。
  - 第 i 个请求发给第 i mod T 个目标，用第 i mod B 个请求体、第 i mod K 把 Key。Key 从 stdin 读（一行一把），不进命令行和任何输出。
  - 两种模式都只往 stdout 写逐请求的原始数据（CSV，第一行是参数）：`seq,start_us,target,status,code,latency_us,warmup,request_id,replayed,retry_after,client_error`，没有 Key 和正文。汇总一律由 `summarize` 从原始数据算：成功、429 `rate_limited`、429 `quota_exhausted`、其它 4xx、5xx、客户端超时、其它客户端错误分开报个数和 p50/p95/p99/最大值（预热的不算，成功的百分位里没有失败的请求），p99 在样本少于 1000 个时写 `insufficient samples`；`sustain` 报成功的吞吐，`burst` 报出发时间的最大差。
  - 先 `docker compose -f compose.yaml -f compose.two.yaml --profile tools build qfbench`：`run` 在镜像缺的时候会现场构建，构建的输出会混进 stdout。
  - 镜像 `quotaforge-qfbench:local` 和 `quotaforge:local` 一样，脚本跑完会留下，下次直接用；不要了用 `docker rmi quotaforge-qfbench:local`。

### 跨实例的检查（`scripts/compose-two-instances.sh`）

```bash
# 在项目根目录下运行
scripts/compose-two-instances.sh   # Compose 项目名 qf-two；8080、8081 被占就不跑
```

同时发的请求都用 `qfbench burst`，一半发给 A、一半发给 B。每项用自己的账户，后面都 `qfctl verify`；时间范围只用 Redis 的 `TIME`。

1. **超扣**：账户的额度正好够 10 次预留，同时发 50 个（`fake-slow-1000`，竞争窗口大）：200 不超过 10，其余都是 429 `quota_exhausted`；已预留 + 已消费不超过上限。
2. **同键**：同一个 `Idempotency-Key`、同样的请求体同时发 20 个：假上游的账单里正好 1 条，账本里这个键只对应一个调用；其余是 409 `idempotency_in_progress` 或重放（`x-request-id` 都是那个调用号）；之后再发是重放。同一个键、不同的请求体同时发 2 个：一个 200，一个 422 `idempotency_key_reused`（请求指纹的判断在所有状态之前，所以后到的一定是 422，不会是 409）。
3. **共享限流**：RPM 为 L = 20 的 Key 同时发 60 个：放行数在 [L, L + L·t/60]，t 是发之前、发之后读到的 Redis `TIME` 之差；被拒的都是 429 `rate_limited`，`Retry-After` 是 1 到 ⌈60/L⌉ = 3 的整数；账本里只有放行的那些。
4. **杀掉一个实例，另一个接手**：A 上发 `fake-billed-hang`（带键），上游已记账、调用 `IN_FLIGHT` 时 `kill -s KILL` A，A 一直不重启。在 B 上带同一个键重试：回收之前 409 `idempotency_in_progress`；B 的后台回收在上界之后把它标成 `USAGE_UNKNOWN`，这时 409 `idempotency_outcome_unknown`；用假上游的账单 `qfctl reconcile -apply` 结清之后，409 `idempotency_response_unavailable`。账本里这个调用只有 reserve、settle 两行，由 `reconcile` 凭账单结清，B 的日志里只标了这一个未知。最后再启动 A，能正常服务。没有心跳，另一个实例也能接手被杀掉的实例留下的调用。
5. **两个实例同时回收、同时清理**：两个实例都停着时，用 SQL 插入 300 个超过上界的遗留调用（一半 `RESERVED`、一半 `IN_FLIGHT`，额度行和账本一并记上），再同时启动两个实例：启动时各跑一轮，同时扫到同一批。`RESERVED` 的都由回收释放、`IN_FLIGHT` 的都标成未知，未知的继续占着预留；两个实例日志里转换的合计正好 300，两边都动过。再停下、插入 3000 个过期的幂等记录（分在 50 个账户上：清理按账户在额度行上串行，只有一个账户时后到的实例总是发现记录已经删掉了）、同时启动：删掉的合计正好 3000，两边都动过。两轮都没有 `reclaim_error`、`purge_error`（也就没有 1213）。回收和清理分两轮：放在一轮里时，先做完回收的实例会把清理全做了。两个实例不是同时起来的，先起来的那个有时 1–3 秒就把一轮做完了，所以每一轮最多做 3 次（每次一批新数据）：正确性每次都核对，“两边都动过”3 次里有一次成立即可，每次两边的计数都写进摘要。

最后核对日志和原始数据里没有 Key、数据库密码、`Authorization` 和请求正文。摘要写到 `evidence/compose-two-instances-summary.txt`。

## 压测

```bash
# 在项目根目录下运行
scripts/compose-bench.sh bench/cloud-YYYY-MM-DD   # 全部场景跑两遍，约 25 分钟；Compose 项目名 qf-bench，结束时 down -v
```

- **怎么测**：`compose.yaml` + `compose.two.yaml` + `compose.bench.yaml`，配置 `deploy/config.bench.json`：只有一个别名 `fake-slow-50`，假上游固定延迟 50 毫秒后回答；Key、账户、上游三层的限额都设得很大但不为 0，每个请求都过 Redis 准入，又不会被拒；账户额度够整场用。`qfbench sustain` 从 Compose 网络里面发（不经宿主机端口转发），闭环：C 个并发各自发完一个再发下一个，预热 5 秒、测 30 秒；全部场景跑完一遍再跑第二遍，两遍都报。单实例的场景把 `quotaforge-b` 停掉；两个实例的场景轮流发给两个实例。
- **口径**：成功的延迟只用成功的请求算，429、其它 4xx、5xx、客户端超时各自分开报（这次全是 0）；预热期间开始的请求不算；吞吐的分子是“开始时间在 30 秒测量窗里的成功请求”，包括窗口结束时还在途、之后才完成的，而窗口开始前（预热里）开始、窗口里才完成的不算，两头大致抵消，最多差约 C ÷（吞吐 × 30 秒）（C 是并发数），所以报的是持续吞吐的近似值；样本少于 1000 个时 p99 写“样本不足”；网关开销 = 同一并发下经 QF 和直连假上游的 p50、p95 之差。

**瓶颈和证据**（证据在 `evidence-run2.txt`，计数是测量的 30 秒里的差）：

1. **一个账户：额度行是热点**。吞吐卡在约 150 次/秒，和并发 16 还是 64、一个还是两个实例都无关。
   - 单实例并发 64：InnoDB 记了 8942 次行锁等待，等待合计 926 秒（30 秒里平均约 31 个事务同时在等）；测到一半时 `data_lock_waits` 有 465 行，32 个连接里 17 个在 `updating`、13 个在 `statistics`（等额度行的锁）；死锁 0。连接池打满：`db_pool` 每 9 秒记一行，每行约 5200 次等连接、等了约 220 秒，`in_use` 32/32。MySQL 只用了约 1 个核（103%），QF 72%：CPU 不是瓶颈，锁是。
   - 每个请求在额度行上排两次队（预留、收尾），行锁持有到提交。150 次/秒相当于每个请求独占这一行约 6.5 毫秒。提交平均 1.13 毫秒、每个请求两次，只占约三分之一；其余是持锁期间的语句往返（预留：条件更新、插调用、插账本、提交；收尾：锁额度行、锁调用、改调用、改额度、插账本、提交）。
   - 对照实验（`durability/`，单实例一个账户，只跑一遍，不是正式场景）：`innodb_flush_log_at_trx_commit=2` 时 188 / 177 次/秒（并发 16 / 64），提交平均 0.72 毫秒；再加 `sync_binlog=0` 时 223 / 225 次/秒，提交平均 0.27 毫秒。上限随提交变快而上升，但远没到 1 ÷（2 × 提交耗时）：持锁期间的语句往返才是大头。默认值不改：这两项是拿持久性换吞吐（崩溃时可能丢掉最近一秒已提交的账），QF 不这么做。
   - 两个实例反而略慢（140 左右）：数据库那边同时等这一行的连接从 32 个变成 64 个（行锁等待合计 1679 秒，平均约 56 个在等），锁只有一把，多出来的只是排队。
2. **16 个账户：提交（刷盘）和 MySQL**。单实例并发 64 约 370 次/秒：行锁等待还有，但每个账户只有约 4 个请求在争；提交平均涨到 7.3 毫秒（测量期间约 2.2 万次提交、2.1 万次 redo 刷盘，连接停在 `waiting for handler commit`），MySQL 用了约 1.7 个核，QF 约 0.9 个核，四个核里加上假上游、Redis、压测工具已经用了约 3 个；连接池也打满（`db_pool` 每 9 秒约 1.1 万次等连接）。
   - 两个实例在同一台机器上反而更慢（约 310 次/秒）：数据库那边的连接从 32 变成 64，同一个 MySQL、同样的四个核，提交平均涨到 10.2 毫秒，行锁等待合计翻倍。每个实例 32 个连接的连接池在这里起了限流的作用；两个实例时数据库那边的并发多了一倍，CPU 没有多。这是 CPU 不够的机器上的结论：刷盘是瓶颈、CPU 有富余时，两个实例并不更慢（见下面的“本机对照”）。
   - 每个请求带新的幂等键时（约 300 次/秒，比不带少约 20%）：预留要多读、多写一行幂等记录，收尾要存快照。
3. **连接池怎么设**：并发 16 时池没打满（没有 `db_pool` 行）；并发 64 时打满。池再大也只是把排队从 QF 挪到数据库里：热点行上等锁的线程更多，提交的队更长（见两个实例的对比）。32 个连接对这台机器的 MySQL 已经够了，瓶颈不在池。
4. **上游连接复用**（`transport/`，各跑一遍，第二组只改了这一处）：Go 默认每个主机只留 2 个空闲连接，同时调同一个上游的请求多于 2 个时，多出来的连接用完就关，QF 这边留下 TIME_WAIT：16 个账户、并发 64 时，测到一半已经有约 9400 个（约 350 次/秒），照这个速度几百次/秒就会用光临时端口。改成每个上游留 100 个空闲连接之后 TIME_WAIT 是 0，吞吐 347 → 387 次/秒，p50 176 → 157 毫秒；一个账户并发 16 时 p95 160 → 138 毫秒；并发 1、直连的场景不变。

**本机对照**（在一台笔记本上原样重跑，`bench/local-2026-10-11/`，第二遍 13 个场景从原始数据复算一致）：

- **机器**：笔记本，Intel Core Ultra 9 275HX，24 个逻辑核，31.4 GiB 内存，NVMe 固态盘，Windows 11；Docker Desktop 29.6.1（WSL2），Compose 5.2.0，Docker 虚拟机 24 个 CPU、15.3 GiB，MySQL 的数据在虚拟机的虚拟磁盘里。MySQL、Redis、Go 的版本和配置和云端相同。

  | 场景 | 并发 | 云端吞吐 | 本机吞吐 | 云端 p50 | 本机 p50 |
  |---|---|---|---|---|---|
  | 直连假上游 | 64 | 1240 / 1238 | 1257 / 1252 | 51.4 / 51.4 | 50.8 / 51.0 |
  | 单实例，1 个账户 | 1 | 15.6 / 15.7 | 16.6 / 14.4 | 63.7 / 63.1 | 59.9 / 71.4 |
  | 单实例，1 个账户 | 16 | 151 / 153 | 85 / 123 | 101 / 98 | 111 / 87 |
  | 单实例，1 个账户 | 64 | 153 / 147 | 48 / 50 | 403 / 420 | 1284 / 1225 |
  | 两个实例，1 个账户 | 64 | 137 / 140 | 84 / 104 | 461 / 439 | 782 / 374 |
  | 单实例，16 个账户 | 64 | 373 / 370 | 421 / 415 | 162 / 163 | 148 / 149 |
  | 两个实例，16 个账户 | 64 | 314 / 306 | 660 / 436 | 185 / 190 | 72 / 139 |

  本机第一遍单实例一个账户、并发 64 时有 1 个 503 `ledger_unavailable`（2057 毫秒）：等额度行的锁超过了账本操作的 2 秒上限，按设计拒绝；其余场景两台机器的失败都是 0。

- **瓶颈不同**（测量期间的计数，证据在两边的 `evidence-run*.txt`）：

  | | 云端 | 本机 |
  |---|---|---|
  | 没有竞争时一次提交（单账户并发 1） | 1.26 / 1.19 毫秒 | 1.91 / 5.07 毫秒 |
  | 单账户并发 64：平均提交 | 1.12 / 1.18 毫秒 | 9.55 / 9.08 毫秒 |
  | 16 个账户并发 64（单实例）：redo 刷盘 | 737 / 705 次/秒 | 274 / 276 次/秒 |
  | 同上：每次刷盘合进的提交 | 约 1.0 | 约 3.1 |
  | 同上：MySQL 的 CPU | 163% / 167%（共 4 核） | 94% / 91%（共 24 核） |

  - 云端：MySQL 用了约 1.7 个核，加上 QF、假上游、Redis、压测工具，4 个核用了约 3 个；提交快（约 1.2 毫秒），每个请求在额度行上的持锁时间里，语句往返占大头。
  - 本机：CPU 很空（MySQL 约 1 个核），提交慢（并发 64 时约 9 毫秒），每秒只刷两三百次 redo；刷盘是瓶颈。两遍之间刷盘的快慢在变（例如没有竞争时的提交 1.9 和 5.1 毫秒），所以本机两遍的差别比云端大。
- **热点行的上限 ≈ 1 ÷（2 × 额度行的持锁时间）**，两边都对得上，持锁时间 = 持锁期间的语句往返 + 提交，只是谁占大头不一样：
  - 本机单账户并发 64：提交约 9.3 毫秒，1 ÷（2 × 9.3 毫秒）≈ 54，实测 48 / 50：持锁时间几乎全是提交。
  - 云端单账户：提交约 1.15 毫秒，只按提交算是 1 ÷（2 × 1.15 毫秒）≈ 435，实测约 150，相当于每个请求持锁约 6.5 毫秒：语句往返占了约三分之二（见上面的刷盘对照实验）。
- **两个实例在两台机器上快慢相反**：
  - 云端 CPU 不够：两个实例时数据库那边的连接从 32 变成 64，多出来的并发只是在 CPU 上排队，提交从约 7 毫秒涨到约 10 毫秒，吞吐反而下降（约 310 对约 370）。
  - 本机刷盘是瓶颈、CPU 有富余：并发多了，一次刷盘能合进更多事务（组提交），提交反而变快，吞吐不降。第二遍两边的刷盘速度差不多（约 275 次/秒），两个实例 436 对一个实例 415，只快约 5%；第一遍两个实例的 660 是在刷盘快得多的时候测的（约 700 次/秒），多出的部分分不清是实例数还是磁盘。单账户也一样：两个实例 84 / 104 对一个实例 48 / 50，提交从约 9 毫秒降到 4–5 毫秒。
  - 所以两个实例快还是慢，看瓶颈在哪：CPU 不够时多实例只是多排队；刷盘是瓶颈、CPU 有富余时，并发多一些反而能把刷盘用得更满。

**局限**：

- 这是一台 4 核云端机器上的数字，所有容器共用 CPU 和磁盘；换一台机器、换一块盘，数字会变，瓶颈也会换（见上面的“本机对照”）。不能当成“QF 能支撑多少 QPS”。
- 闭环压测：并发固定，延迟高了发得就少，会低估排队（真实流量不会因为 QF 慢了就少来）。
- 两个实例在同一台机器上、用同一个 MySQL，测的是共享状态时的正确性和开销，不是扩容。
- 压测期间库越跑越大（`calls` 表第二遍开始时约 7 万行，第二遍最后一个场景开始时约 13 万行）；每个场景开始时的行数记在证据里。
- 假上游固定 50 毫秒、请求体很小；真实上游慢得多（真实冒烟里聊天的中位数约 4 秒），同样的吞吐下在途的请求多得多，连接池、上游连接数的压力会不一样。

**优化方向**（只讨论，还没有做）：

- **缩短持锁时间**：预留时先插调用记录和账本行，最后才对额度行做条件更新、紧接着提交，额度行的持锁时间从“四条语句 + 提交”降到“一条语句 + 提交”；收尾同理。代价：要重新论证锁的顺序（现在一律先锁额度行，见[锁的顺序](ledger.md#额度和账本)），额度不够时要回滚已经插的行。它只能去掉语句往返那部分，提交仍在持锁期间：刷盘慢的机器上（见“本机对照”，提交约 9 毫秒），热点账户要靠下面的拆份或批量结算。
- **热点账户的额度拆成几份**（N 个子额度行，预留随机落一份，不够再试别的）：吞吐约乘 N。代价：总额度的判断变成“各份之和”，额度快用完时会出现“总的够、落到的那份不够”的假拒绝，要合并或再平衡；账本校验要按份汇总。
- **批量结算**：收尾不逐个改额度行，先写调用和账本，额度行由后台按批汇总。代价：已消费有延迟，超用的判断不及时；崩溃时要能重放未汇总的部分。
- **准入和账本异步化**（例如先在 Redis 里扣额度，再异步落 MySQL）：最快，但额度的权威从 MySQL 挪到了 Redis，两者之间没有跨库事务，Redis 丢数据或两边不一致时会多放，要对账兜底。和现在“额度只以 MySQL 为准”的守则相冲突。
- 放宽刷盘（`innodb_flush_log_at_trx_commit`、`sync_binlog`）只是对照实验，不是方向。
