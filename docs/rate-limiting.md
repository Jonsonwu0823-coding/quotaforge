# 限流

## 限流（Redis）

多个 QF 实例共享一组令牌桶，放在 Redis 里。额度（账本）管“总共能用多少”，限流管“每分钟最多用多快”。额度和账本的权威仍是 MySQL。限流的 Redis（`qf-redis`）只放限流的状态；[嵌入缓存](api.md#嵌入缓存)放在另一个 Redis 里，原因见[嵌入缓存](operations.md#嵌入缓存)。

- **放在哪一步**：估算之后、预留之前（准入）。被限流的请求不写数据库、不占预留，日志里没有 `reserved_tokens`、`call_status`，账本里也没有这次调用。`GET /v1/calls/{id}` 不限流。
  - 代价：Redis 和 MySQL 之间没有跨库事务。准入通过、预留却没成（额度不够、账本不可用、幂等的重放和 409、422）时，这次的 RPM 不退，TPM 全退（见下面的修正）；重放和幂等的 409 也算一次请求，占 RPM。
  - 嵌入缓存命中的请求也先过准入（命中也要写一行账本，不能绕开限流）：占 1 个 RPM，TPM 全退，和重放一样。
- **三层，每层两个指标**：Key、账户、上游，各有每分钟的请求数（RPM）和 token 数（TPM）。**限额 0 表示这一层的这个指标不限。**
  - Key、账户的限额存在 MySQL（`api_keys`、`accounts` 的 `rpm_limit`、`tpm_limit`），用 qfctl 设；每个请求按库里现在的值，改了立即生效。迁移前已有的 Key 和账户都是 0。
  - 上游的写在配置里（`upstreams[].rpm`、`tpm`），保护的是 QF 用的那把上游 Key 的总量，所以按上游限，不按模型细分。别名有多个目标时，上游层检查的是选中的目标的上游；换上游时桶跟着走，见下面的[多个上游](#多个上游)。
  - 限额是 0 到 10¹² 的整数，qfctl 的参数和配置文件按同一条规则校验。
  - **要停用一把 Key，用 `qfctl key revoke`**：把限额设成 0 是不限，不是停用。
  - 一个请求要检查的桶，就是三层里限额不为 0 的那些（最多 6 个）；一个都没有的请求不碰 Redis。
- **令牌桶**：每个桶的容量是每分钟的限额 L，每毫秒补 L/60000，补满为止。RPM 桶每个请求花 1；TPM 桶花这次的估算，也就是预留量（见[额度和账本](ledger.md#额度和账本)）。
  - 一次准入把涉及的所有桶放进一个 Lua 脚本（`internal/ratelimit/bucket.lua`），在 Redis 里原子执行：先把每个桶补到现在，每个桶都满足“令牌数 ≥ min(花费, 容量)”才放行，并在每个桶里扣掉花费；只要有一个不满足，就一个都不扣（全有或全无），返回 429。
  - 时间只取脚本里 Redis 的 `TIME`，QF 不传时间，所以多个实例的时钟不一致也没关系。
  - 花费超过整桶的请求（估算比每分钟的 TPM 限额还大）：桶满时放行，桶变成负数，之后的请求要等它补回来。不这样的话，这种请求永远进不来。
  - 桶不存在就当作满的。每次写桶都设过期时间：补满所需的时间再加 1 秒。空闲的桶到期删掉，等于满桶，不会留下来。
  - 桶的 key 是 `qf:rl:<层>:<编号>:<指标>`，例如 `qf:rl:key:42:rpm`、`qf:rl:upstream:bailian:tpm`。
- **上界**：从满桶开始，任意一段时间 t 秒里，一个桶的扣除合计：
  - 每次花费都不超过 L 时，不超过 L + L·t/60；
  - 有超过整桶的请求时，再加上最后一次放行的请求超出 L 的部分。这种请求只在桶满时放行，之后桶是负数，要等补回来；
  - 这里的“扣”是准入按估算扣的、减去修正退回的。实际用量比估算多时，修正会再扣（桶变负），这部分是事后记上的，不受准入的上界约束，只会让之后的请求多等。
  - 脚本在 Redis 里原子执行，多个实例、多个连接同时准入也是这样。RPM 每次花 1，严格满足第一条。
- **TPM 要配多大**：TPM 的限额要远大于单次请求的估算。估算偏保守：输入是转发的请求体字节数，输出是 `max_tokens`，没写就是模型的 `default_max_tokens`。真实冒烟里单次聊天的估算最多约 17,300 tokens，而聊天平均每次实际约 3,200。估算超过整桶的请求要等桶满才放行，接近整桶的请求也常常要等。
- **TPM 的修正**：调用结束后，按网关自己判定的结局（日志的 `outcome`）修正这次扣过的每个 TPM 桶，和账本写没写成功无关。加回之后不超过容量；RPM 不退。

  | 结局 | 修正 |
  |---|---|
  | `SETTLED` | 加回“估算 − 实际的 total”。实际比估算多时就是再扣，桶可以变负，但一次最多再扣这个桶的容量 L（见下） |
  | `USAGE_UNKNOWN` | 不动：上游可能已经计了费，按估算算是保守的 |
  | 其余 | 全部加回：没有预留（额度不够、账本不可用、幂等的重放和 409、422、嵌入缓存命中的 `CACHED`）、发送意图没落成、没发出、连接没建立、上游 4xx |

  - 再扣的上限：实际直接信上游。上游报的用量离谱时（例如 prompt_tokens 是 100 万），不封顶的话这个桶会被压成很大的负数，要几个小时才补回来；落在上游那一层就挡住所有账户。所以一次修正每个 TPM 桶最多再扣 L：桶最低到“准入后 − L”，一分钟补回。这只是不让一次离谱的用量把桶压很久；账本不受影响，照旧按实际的 total 结算。

  - 修正在写回之后、写日志之前，在请求的处理函数返回之前执行。net/http 要等处理函数返回才把响应发完，所以客户端会等这次修正：通常约 1 毫秒，Redis 很慢时最多 0.5 秒。
  - 修正失败（Redis 出错、超时）只记日志（`rate_limiter_error`），不影响已经得到的结果，也不重试。这时桶里多扣着估算，偏保守。
- **Redis 出错时：拒绝，不放行**。准入时 Redis 出错或超时，返回 503 `rate_limiter_unavailable`，不预留、不调上游。只影响要检查桶的请求。
  - 每次 Redis 操作（准入、修正）最多 0.5 秒，由 context 限住。go-redis 设了 `ContextTimeoutEnabled`：不设的话，Redis 接受连接却不回答时要等它自己几秒的读超时。
  - 拨号也限在这 0.5 秒里，只试一次（`DialTimeout`、`DialerRetries`）。go-redis 在后台拨号，拨号不随请求取消：默认每次 5 秒、最多 5 次的话，Redis 停着时，名字解析（Docker Desktop 上约 4 秒才失败）会活得比请求久，Redis 回来之后的请求还要等这次过时的查询。
  - 拨号限住之后，还有两种情形恢复得慢一些，限住拨号之前就是这样：Redis 停着时，几个请求同时拨号会共用一次名字解析，恢复后要等这次查询结束（Docker Desktop 上约 4 秒）；停着时失败的拨号累计到连接池大小（默认 10 × CPU 数）之后，go-redis 不再拨号，改成每秒探测一次，Redis 回来后最多约 1 秒才回到 200。
  - 拨号的上限是 0.5 秒也有代价：拨号（名字解析加建连）每次都超过 0.5 秒时，限流一直连不上 Redis，要检查桶的请求都是 503，原因看调用日志的 `rate_limiter_error`。
  - 不自动重试（`MaxRetries: -1`）：准入不是幂等的，读超时之后重试可能扣两次。
  - 准入超时有一种结局：脚本在 Redis 里已经执行了，回复却超过 0.5 秒才到。这时返回 503，桶里已经扣了，也不退（不知道到底扣没扣）。偏保守，和“修正失败多扣着”是同一类代价。
  - Redis 恢复后不用重启 QF：go-redis 自己重连，Redis 重启后脚本缓存是空的，第一次会自动改发完整的脚本。冒烟验证了：Redis 停了时请求是 503，重新起来后第一个请求就是 200。
  - QF 启动时不连 Redis；`/healthz` 不看 Redis，它只表示进程活着。
  - go-redis 自己的日志丢掉：影响请求的错误都记在那次调用的日志行里。Redis 的 URL（可能带密码）不进日志和报错；错误文字（`rate_limiter_error`）里会有 Redis 的主机和端口。
- **不持久化**：Compose 里的 `qf-redis` 是 `--save '' --appendonly no`。限流的状态丢了只会让桶变满：Redis 重启之后，每个桶最多多放一整桶。
- **只支持单机 Redis**：Redis Cluster 下，一次脚本用到的 key 必须在同一个槽，三层的 key 做不到。要用 Cluster，要么把它们全放进一个 hash tag（集中在一个分片上），要么拆成逐层检查、放弃全有或全无。

## 多个上游

别名有多个目标时（见[多个上游](operations.md#多个上游)），上游层的桶只为可能收到请求的那个上游扣：

- **准入**：Key、账户两层只在调用开始时准入一次。上游层检查选中的目标的上游。选目标在准入之前，只看熔断，不看上游层的桶：选中的上游的桶不够，就是 429 `rate_limited`，不改去别的目标。
- **换上游**（前一个上游拨号失败，确定没收到请求）：新上游先准入，只准入上游层，花费还是这次的预留量（换上游时预留量不变）。
  - 准入不过（被限，或 Redis 不可用）就不换：返回前一次的错误（502 `upstream_unavailable`），调用照常按“确定没发出”释放。日志照样记下拒绝的桶（`rate_limited_by`）或 Redis 的错误（`rate_limiter_error`），`qf_rate_limited_total` 也计一次。
  - 准入的上限从这次调用所有尝试共用的期限派生：期限快到时准入也跟着截止，不会让换上游超过用途的超时。
- **修正**：
  - 换走的上游确定没收到请求，它的 TPM 桶不论结局都全部加回，RPM 不退；
  - Key、账户两层和最后那个上游，照上表按结局修正；
  - 新上游准入过、账本却没改道成（被回收了、账本出错）时，没发给它；调用按“确定没发出”收尾，它的 TPM 和别的桶一样全部加回；
  - 这些都在调用结束时的同一次修正里做，尝试之间不多等一次 Redis。
